CHAPTER 3. THEORETICAL BACKGROUND AND TECHNOLOGIES

Overview

Chapter 2 defined the user needs and functional requirements of the AI-assisted interior layout design system. This chapter presents the theoretical background and technologies that support those requirements. The discussion focuses on the concepts directly used by the implemented system: indoor layout representation, constrained furniture placement, LLM-assisted planning, asset-grounded scene synthesis, 3D snapshot conditioning, generative image models, image editing, and evaluation metrics.

The main design principle of the system is to separate semantic reasoning from geometric feasibility. Language models are useful for interpreting the brief, grouping objects, and expressing spatial intentions, but final furniture coordinates must still be checked by deterministic geometry and evaluation modules. This principle is consistent with prior work on interior layout optimization and recent LLM-based scene generation systems [1], [2], [5], [7], [8], [9].

3.1 Indoor Layout Representation

The layout representation used in this thesis is a compact 2D-first scene model. A layout can be written as L = (P, G, O, A), where P is the room polygon in millimeters, G is the set of door and window openings attached to wall edges, O is the set of furniture objects, and A stores style, material, and rendering metadata. Each object is represented as o_i = (type_i, c_i, s_i, theta_i, h_i, front_i, meta_i), where c_i = (x_i, y_i) is the center point, s_i = (w_i, d_i) is the footprint size, theta_i is the rotation, and h_i is the height.

The use of a single physical unit is important. The frontend may display a floor plan in pixels, but the backend, solver, and 3D preview use stable millimeter coordinates. With this shared coordinate system, the same object footprint R_i(theta_i) can be checked for containment, overlap, opening clearance, and access paths before it is converted into a 3D scene or rendered image.

Research on indoor scene synthesis commonly represents a room by its floor plan and a set of object attributes such as category, position, size, and orientation [3], [4]. The implemented representation follows this general idea but remains application-oriented: it stores enough geometry for interactive editing, deterministic validation, 3D preview, and image conditioning, while avoiding unnecessary architectural details that would make the user workflow harder.

3.2 Geometric Constraints in Furniture Placement

Furniture placement is a constrained search problem over layout variables X = {(c_i, theta_i)}. A candidate layout is feasible only when its blocking footprints stay inside the room polygon, do not overlap other blocking footprints, preserve door and window clearance, keep a path from openings to the room center, and respect locked user placements. In compact form, the hard constraints include R_i(theta_i) subset P_room, area(R_i ∩ R_j) = 0 for blocking pairs, dist(R_i, opening_k) >= clearance_k, and an unblocked path(opening_k, center(P_room)).

Classical furniture-layout research shows why these constraints cannot be handled by text alone. Merrell et al. encode interior design guidelines as terms in a density function and sample furniture arrangements interactively [1]. Yu et al. formulate furniture arrangement as an optimization problem over spatial and hierarchical relationships, including accessibility and visibility priors [2]. Following this view, a solver can rank feasible candidates by L* = arg min_{L in F} E(L), where E(L) = sum_m lambda_m phi_m(L) + sum_n mu_n psi_n(L). The phi_m terms penalize feasibility violations, while the psi_n terms express soft preferences such as wall anchoring, visibility, adjacency, balance, and circulation.

The implemented system therefore combines semantic planning with deterministic geometric validation. LLM stages propose what should be placed and why; solver stages enumerate, repair, validate, and score where objects can be placed. This separation reduces hallucinated coordinates and makes the output auditable, because invalid layouts can be rejected or repaired before they reach the final gallery.

3.3 LLM-Assisted Planning and Structured Agents

Large language models are used as reasoning components rather than as direct coordinate generators. The pipeline decomposes the task into narrower stages: room interpretation, style-policy compilation, semantic cluster generation, request-contract extraction, tier and count decisions, cluster merging, concept generation, solving, final styling, and gallery selection. Each stage produces a structured JSON artifact that can be stored, inspected, replayed, or ablated.


Figure 3.3. Transformer architecture, adapted from Vaswani et al. [16].

Figure 3.3 illustrates the core structure behind many modern LLMs. Tokens are converted into embeddings, enriched with positional information, and processed through attention and feed-forward blocks. In this thesis, this architecture explains why LLMs are suitable for interpreting design briefs and object relations. The system still avoids using the LLM as a direct coordinate generator, because language reasoning alone does not guarantee geometric validity.

This organization follows the broader agentic idea that language models can interleave reasoning with actions and external validation [6]. In the interior-design domain, recent systems also use LLMs to plan objects and relations before relying on placement or optimization algorithms. LayoutGPT treats LLMs as visual planners that generate spatial layouts from text [5]. I-Design uses multiple LLM agents to convert user input into a feasible scene graph and then places objects algorithmically [7]. Holodeck uses an LLM to produce spatial relational constraints and then optimizes a 3D scene to satisfy them [8]. FlairGPT similarly converts LLM outputs into a layout graph solved by constrained optimization [9].

The request contract is important in this thesis because user briefs often contain implicit priorities. For example, a desk near a window may be optional in a small bedroom, but a bed and wardrobe are required. The request contract makes such priorities explicit before tier counting and solving. This helps the system distinguish required objects, target-if-viable objects, and decorative support objects, which is necessary for both generation and evaluation.

3.4 Indoor Scene Synthesis and Asset-Grounded Layouts

Indoor scene synthesis studies how to generate plausible object sets and arrangements for a given room. ATISS models indoor scenes as unordered sets of objects conditioned on room type and floor plan [3]. DiffuScene uses a denoising diffusion model over unordered object attributes, including location, size, orientation, semantics, and geometry features [4]. These approaches demonstrate that indoor layout generation is not only a text problem; it also requires structured object attributes and physical plausibility.

The system in this thesis does not train a new scene-synthesis model. Instead, it uses LLM planning and deterministic solving over an inventory of available furniture assets. The inventory connects abstract furniture categories with concrete items, dimensions, style tags, materials, optional prices, colors, and 3D model metadata. If a GLB model exists, the frontend can load it in the 3D preview. If a model is missing or unreliable, proxy geometry is generated so that layout validity does not depend on asset availability.

This asset-grounded approach is suitable for an applied thesis because it keeps the generated design editable. Users can still move objects, compare variants, and reuse the same design structure for preview and image generation. It also avoids the common failure mode in which a generated image looks plausible but no longer corresponds to a concrete object list or editable layout.

3.5 3D Preview and Snapshot Representation

The 3D preview is treated as a representation bridge rather than a separate theory module. It reconstructs the selected 2D layout as a browser scene and exports a snapshot containing the source view, camera metadata, visible objects, screen-space boxes, openings, and optional references. The important point for this chapter is that the snapshot becomes a conditioning signal for Section 3.6: it preserves geometric evidence so that generated or edited images can be checked against the original layout.

3.6 Layout-Conditioned Image Generation and Editing

Image generation converts the 3D blockout into a more realistic interior visualization. The current experiments use gpt-image-2 as the provider image model for generation and editing, but its internal architecture is not public; therefore, this thesis abstracts it as a text-and-image-conditioned generative image model [19]. The relevant theoretical basis is diffusion and latent diffusion: DDPMs learn to reverse a gradual noising process [18], while latent diffusion performs denoising in a compressed latent space and uses conditioning mechanisms such as cross-attention for text or spatial inputs [10].

Text alone is weak at preserving exact spatial layouts. Conditional-control methods such as ControlNet show that additional spatial signals, including edges, depth, and segmentation, can improve control over diffusion outputs [11]. TKNT follows the same principle at the application level: the source 3D view, object contract, visible-object map, preset style-lighting-scenery references, and optional locked-geometry references provide conditioning evidence beyond a plain prompt. Figure 3.4 summarizes this abstraction.

Image editing uses the same conditional-generation view. Instruction-based editing methods such as InstructPix2Pix show that an input image and a written instruction can jointly define an edit [12]. In TKNT, the edit operation, target object ids, normalized bounding boxes or masks, replacement references, target colors, and preservation constraints define what may change and what must remain fixed. The theory point is local conditioning and preservation, not retraining a new image model.

3.7 Evaluation Metrics for Layout and Image Quality

The evaluation must reflect two different outputs: editable layouts and rendered images. For layout auto-fill, every system output is normalized to a common 2D schema before scoring. Geometry validity checks out-of-bounds area, overlapping blocking furniture, opening clearance violations, and door-to-center path blockers. Request-following checks required objects, count ranges, relations, and opening-related preferences; in simple-simple cases, the checks are deliberately lighter and focus on a minimum number of valid solid objects plus the presence of a room-primary anchor. Arrangement reasonableness and valid-object count then capture whether the result is usable as a furnished room, not merely a set of valid rectangles.

For ablation cases where the four primary layout scores do not fully expose the removed component, the stability holdout adds a holistic stability view. This view combines the canonical production score with style-material consistency, gallery diversity, and reliability. The style-material group checks whether the output keeps the intended density, center openness, wall anchoring, decor density, daylight usage, palette family, and material family. Gallery diversity checks whether the system produces multiple distinct viable candidates instead of a single brittle answer. These metrics are used only to broaden the evaluation lens; they do not replace the main layout benchmark.


Figure 3.5. LLaVA-style vision-language architecture, adapted from Liu et al. [17].

Figure 3.5 shows how a VLM connects visual features with language reasoning. A vision encoder extracts image representations, a projection layer maps them into the language-model space, and the language model produces a textual response. This mechanism is relevant to the image-evaluation stage of the system, where the generated render must be checked against layout, object, opening, and camera constraints.

For generated and edited images, traditional full-reference metrics such as SSIM and learned perceptual metrics such as LPIPS are useful references but are not sufficient for this system [13], [14]. The actual evaluation therefore combines blank-image checks, provider runtime and token usage, vision-based layout fidelity, and structural preservation. Layout fidelity checks camera framing, room shell, openings, object inventory, object position, object scale, object silhouette, and unauthorized additions. Structural preservation is estimated with edge-map matching, monocular-depth similarity, and DINOv2 patch/object feature similarity, because self-supervised visual features can remain meaningful even when texture and lighting change [15].

The image-flow metrics also include preset fidelity and edit-specific fidelity. Preset fidelity checks whether the generated image follows the selected style, lighting, and scenery intent. Edit-instruction fidelity checks whether the requested add, remove, replace, or recolor operation was performed, while edit-scope fidelity measures whether changes outside the target region remain limited. These metrics are intentionally strict: a photorealistic image may look good but still fail if it moves the camera, replaces the sofa, changes a window, alters object scale, or edits outside the requested scope.

3.8 Web Technologies Used in the System

The application is implemented as a web system. The frontend uses a React single-page application for the design workspace, 2D editing, 3D preview, account views, and render controls. The backend uses FastAPI to expose layout-generation, artifact, authentication, inventory, saved-layout, and image-rendering endpoints. PostgreSQL stores persistent users, sessions, inventory, saved layouts, and generated renders.

The system uses server-sent events for long-running pipeline progress and image generation events. This is necessary because layout generation and image rendering may take longer than a normal request-response interaction. The frontend can show stage status while the backend writes reproducible artifacts into case folders for debugging and evaluation.

The 3D preview uses a browser-based scene graph so that the same design can be inspected interactively before image generation. This design keeps the core workflow continuous: the user describes the room, receives editable layout variants, adjusts them when needed, inspects the result in 3D, and then creates or edits a photorealistic render from the selected snapshot.

3.9 Chapter Conclusion

This chapter presented the theoretical and technological basis of the system. The key idea is to keep semantic reasoning, geometric feasibility, snapshot conditioning, image generation/editing, and evaluation as separate but connected components. Prior research supports this separation: LLMs are useful for planning and relation extraction, constrained optimization and geometry checks remain necessary for reliable placement, and generative image models require explicit conditioning and strict evaluation when layout fidelity matters. Chapter 4 explains how these concepts are implemented and evaluated in the TKNT system.
